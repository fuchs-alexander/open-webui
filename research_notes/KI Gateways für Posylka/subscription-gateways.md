# Subscription-capable unified gateways for Posylka

Research snapshot: 2026-10-26. Research only: no installation, deployment, credentials, provider calls, or account authorization. Existing modified `AGENTS.md` was left untouched. Evidence labels: **documented** = upstream documentation; **source-inspected** = implementation inspected, not executed; **claimed** = upstream marketing/README; **untested** = no acceptance test against Posylka Open WebUI v0.12.4. All release/activity observations are GitHub API snapshots, not guarantees of quality. Moving default branches can contain unreleased changes; important CLIProxyAPI SIWC findings were also checked at release tag v8.0.43.

## 1. Can one ChatGPT Pro subscription legitimately serve every WebUI user, and what do OAuth claims mean?

### Takeaway

No researched gateway establishes permission to turn one personal Pro subscription into a shared team inference account. Crucially, **current CLIProxyAPI v8.0.43 does contain a real direct SIWC/public-API flow**; classifying every subscription gateway as exclusively an unofficial Codex-backend proxy would be incorrect. This technical improvement does not establish authorization for the requested multi-person sharing. [OpenAI SIWC](https://developers.openai.com/siwc/token-sharing-open-source); [CLIProxyAPI release source](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.43/internal/auth/codex/siwc_auth.go); [OpenAI account-sharing policy](https://help.openai.com/en/articles/10471989-openai-account-sharing-policy)

### Cited Findings

- **Official OpenAI SIWC plan usage exists**, rather than all third-party plan usage necessarily requiring backend emulation. Open-source/local apps request the user's permission for eligible Responses requests; a dynamically issued client ID is bound to that user and selected workspace, while each installation/VM has its own persistent host ID. Documentation directs paid or remotely hosted apps to an interest form. A self-hosted VM for the same user's tool is explicitly contemplated; this is not evidence for pooled use by arbitrary end users. [Overview](https://developers.openai.com/siwc/token-sharing-open-source); [Self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms)
- **OpenAI account-sharing restriction:** the official Help Center search result states the account is for the individual creator, others should create their own account, and sharing is not allowed. Direct fetch returned HTTP 403 during this research; the source was available through the search integration, so treat this as official indexed text, not a successful full-page fetch. This conflicts with the user's desired one-Pro-for-all model; private WebUI logins or downstream gateway keys do not themselves create extra subscription entitlements. [Policy](https://help.openai.com/en/articles/10471989-openai-account-sharing-policy)
- **SIWC public Responses preview is constrained:** HTTP requires `store:false`, `stream:true`, array input, developer/instructions rather than explicit system message items, and no HTTP `previous_response_id`. Temperature, token-limit fields, metadata and numerous other fields are unsupported. Function/custom tools require namespaces or `additional_tools`; hosted MCP, tool_search, image generation, file search and Code Interpreter are unsupported on this route. Local tool execution is distinct from hosted tools. [Official limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)
- **CLIProxyAPI SIWC is source-inspected, not just an OAuth marketing claim:** tagged v8.0.43 defines dynamic registration, resource `https://api.openai.com/v1`, `chatgpt.tokens.use.direct`, PKCE, persistent host UUID and issued-client-ID checks. Current executor selects SIWC separately from original Codex credentials and defines public API base `https://api.openai.com/v1`; both SIWC and legacy paths coexist. This is strong evidence of intended official direct flow, not a live authorization or correctness audit. [Tagged auth implementation](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.43/internal/auth/codex/siwc_auth.go); [Executor credential handling](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/codex_executor_auth.go); [Request normalization](https://github.com/router-for-me/CLIProxyAPI/blob/main/internal/runtime/executor/codex_executor_request.go)
- **9Router Codex is demonstrably the legacy backend path:** source provider points to `https://chatgpt.com/backend-api/codex/responses`, forces stream and supplies Codex-CLI identity headers. Its UI metadata marks the provider deprecated with `RISK_NOTICE`. OAuth here is not evidence of the new SIWC direct scope or public endpoint. [Source](https://github.com/decolua/9router/blob/3a978a631ad65529c06e48ce495092d5bba29f46/open-sse/providers/registry/codex.js)
- **OmniRoute's inspected Codex adapter likewise uses the backend path**, `https://chatgpt.com/backend-api/codex/responses`; its WebSocket documentation describes tunneling to the same backend. There are other adapters including Codex app-server, but that name alone does not prove official SIWC configuration. [Codex source](https://github.com/diegosouzapw/OmniRoute/blob/412319f0bdda06a1c7db93dd62bdf8b6317edc1e/open-sse/config/providers/registry/codex/index.ts); [Released API reference](https://github.com/diegosouzapw/OmniRoute/blob/v3.8.52/docs/reference/API_REFERENCE.md)
- **Claude OAuth and Claude API keys have materially different permission models.** Anthropic explicitly says third-party developers may not offer Claude.ai login in their apps or route requests through Free/Pro/Max credentials on behalf of users; developers should use API authentication or supported cloud providers. Ordinary subscription usage is for native Anthropic applications. Hosting the unmodified Claude Code binary with each end user's own authentication is a separate, limited exception—not permission for a subscription-to-OpenAI-compatible relay. [Official legal/compliance documentation](https://code.claude.com/docs/en/legal-and-compliance)

### Inferences

- User insistence cannot resolve the entitlement conflict. Present shared-Pro routing as a technically possible configuration in some tools, **not a supported production entitlement**; obtain written OpenAI approval for this exact hosted/multi-user scenario before recommending it. Even the best direct-SIWC implementation does not settle that issue. [Account policy](https://help.openai.com/en/articles/10471989-openai-account-sharing-policy); [SIWC scope](https://developers.openai.com/siwc/token-sharing-open-source)
- For Claude in shared WebUI, use the separately billed Anthropic API or OpenRouter with explicit approval, not a Pro/Max OAuth relay. This is a policy constraint, not just refresh-token fragility. [Anthropic restrictions](https://code.claude.com/docs/en/legal-and-compliance)

### Gaps

- No written provider approval was found for Posylka sharing one personal Pro account among all WebUI users. Exact private-business/hosted-app SIWC eligibility remains an approval question. [SIWC interest/eligibility notice](https://developers.openai.com/siwc/token-sharing-open-source)
- No credentialed test was performed. SIWC consent, plan eligibility, model discovery, token refresh, translation correctness and actual account suspension behavior remain unverified. Source-supported capability is not a successful live integration. [CLIProxyAPI implementation](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.43/internal/auth/codex/siwc_auth.go)

## 2. How do CLIProxyAPI, Plus, 9Router, OmniRoute and LiteLLM compare?

### Takeaway

**CLIProxyAPI is the most compelling focused SIWC adapter to investigate next; OmniRoute has the broadest claimed integrated control plane; LiteLLM is the strongest documented alternative for multi-user governance and ordinary paid APIs.** None is presently accepted/tested for this deployment, and none authorizes shared personal subscriptions. [CLIProxyAPI](https://github.com/router-for-me/CLIProxyAPI); [OmniRoute](https://github.com/diegosouzapw/OmniRoute); [LiteLLM keys](https://docs.litellm.ai/docs/proxy/virtual_keys)

- **LiteLLM's subscription path has concrete documented operational caveats:** proxy cannot conduct interactive device login itself; refresh needs writable persistent token storage; concurrent refresh and non-atomic file reads introduce race failures; revoked-but-not-expired access token 401 does not automatically refresh. ### Inferences

- For just the three target providers, Plus adds fork provenance/update work without a demonstrated requirement missing in mainline. Mainline's tagged SIWC evidence currently makes it the better narrow research candidate. [Mainline SIWC](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.43/internal/auth/codex/siwc_auth.go); [Plus overview](https://github.com/kaitranntt/CLIProxyAPIPlus)
- If the requirement changes to permission-compatible shared **API** access, LiteLLM is a stronger multi-user baseline than a CLI-account pool. If rich routing/governance in one package matters more than minimality, OmniRoute deserves a separate security and release-specific evaluation. [LiteLLM governance](https://docs.litellm.ai/docs/proxy/virtual_keys); [OmniRoute authorization](https://github.com/diegosouzapw/OmniRoute/blob/release/v3.8.53/docs/architecture/AUTHZ_GUIDE.md)

### Gaps

- No end-to-end tests verified parallel tool calls, streamed tool argument assembly, stop reasons, reasoning replay, native WebUI tools/Higgsfield MCP, or multi-user attribution in any candidate. Readme provider/model counts and test counts were not independently validated. [CLIProxyAPI claims](https://github.com/router-for-me/CLIProxyAPI); [9Router claims](https://github.com/decolua/9router); [OmniRoute claims](https://github.com/diegosouzapw/OmniRoute)
- Hard tenant isolation, credential encryption completeness, independent audits, exact Plus advantages and rate-limit behavior at a pinned release were not fully audited. Source/file inspections are intentionally narrow, and absence of SIWC-named paths is not proof of absence of every possible SIWC implementation. [Plus tree](https://api.github.com/repos/kaitranntt/CLIProxyAPIPlus/git/trees/main?recursive=1)

## 3. What is practical and safe for Posylka production?

### Takeaway

Do not deploy the requested shared personal subscription configuration as “supported.” Separate **entitlement approval**, **network/security hardening**, and **WebUI acceptance tests**. The lowest-complexity next research step is pinned CLIProxyAPI SIWC evaluation after provider/use-case clarification; the safer shared production baseline is explicitly approved paid API access with a governed gateway. [SIWC scope](https://developers.openai.com/siwc/token-sharing-open-source); [Anthropic policy](https://code.claude.com/docs/en/legal-and-compliance); [LiteLLM keys](https://docs.litellm.ai/docs/proxy/virtual_keys)

### Cited Findings

- **CLIProxyAPI is not loopback-only by default:** sample config host `""` means all IPv4/IPv6 interfaces; port 8317. Management remote access defaults false and management secret is empty. Client proxy API keys are a separate setting with placeholders. Do not confuse protected/disabled management with protected inference or publish the example unchanged. Config also documents optional request cloaking/system-prompt replacement for Claude. This deserves compatibility/policy scrutiny, not use as an evasion recommendation. [Tagged sample config](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.43/config.example.yaml)
- **9Router example is unsafe to expose unchanged:** `INITIAL_PASSWORD=change-me`, `JWT_SECRET=change-me-to-a-long-random-secret`, `AUTH_COOKIE_SECURE=false`, `REQUIRE_API_KEY=false`. These are example values; actual installation path may override them, so this is not a claim that every running instance is open. Its optional cloud-sync settings point to `9router.com`; local-only should be an explicit reviewed choice. [Environment contract](https://github.com/decolua/9router/blob/3a978a631ad65529c06e48ce495092d5bba29f46/.env.example)
- **OmniRoute distinguishes network isolation from auth:** environment docs explicitly say `REQUIRE_API_KEY=false` is default and Docker app publish defaults to loopback; broadening bind without enforcing keys exposes an anonymous inference proxy. Environment sample has `INITIAL_PASSWORD=CHANGEME`; whole-database encryption is optional/blank by default, separate from key-at-rest encryption. Authorization docs describe scoped management access, protected operator mutations and first-run bootstrap. Some MCP scope enforcement is opt-in, so feature-rich does not mean everything is locked by default. [Environment](https://github.com/diegosouzapw/OmniRoute/blob/412319f0bdda06a1c7db93dd62bdf8b6317edc1e/.env.example); [Authorization](https://github.com/diegosouzapw/OmniRoute/blob/412319f0bdda06a1c7db93dd62bdf8b6317edc1e/docs/architecture/AUTHZ_GUIDE.md)
- **OmniRoute's operational surface is unusually broad:** README advertises embedded service management, plugin marketplace, MCP management, browser/CLI integrations, compression, MITM features and many provider adapters. README also warns Docker's 1024 MB V8 heap default is for light chat and long overlapping coding contexts can need much more memory. Marketing “production controls” and huge test declarations are not a performance certification. [README](https://github.com/diegosouzapw/OmniRoute); [Security policy](https://github.com/diegosouzapw/OmniRoute/blob/release/v3.8.53/SECURITY.md)
- **Governance needs real caller identities:** LiteLLM can enforce key/user/team limits, but if WebUI presents only one shared server key then the gateway naturally sees one key, not automatically distinct users. 9Router key records identify a named key/machine with access rules, not a proven WebUI user identity integration. [LiteLLM ownership/limits](https://docs.litellm.ai/docs/proxy/virtual_keys); [9Router keys implementation](https://github.com/decolua/9router/blob/3a978a631ad65529c06e48ce495092d5bba29f46/src/lib/db/repos/apiKeysRepo.js)
- Open WebUI documents connecting OpenAI-compatible providers through configurable connections; that supports the architectural fit of a gateway endpoint but is not a specific certification of these adapters, v0.12.4 semantics or SIWC normalization. [Open WebUI connection docs](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-openai.md)

### Inferences

- **Conditional shortlist:** (1) CLIProxyAPI for minimal direct-SIWC technical investigation; (2) LiteLLM for ordinary OpenAI/Claude API + OpenRouter and governed multi-user use; (3) OmniRoute when its extra routing/quota features justify a larger surface; (4) 9Router for a private experimental UI-led evaluation; (5) Plus only for a demonstrated missing provider. This is an assessment from evidence above, not a deployment authorization or tested benchmark. [Mainline](https://github.com/router-for-me/CLIProxyAPI); [LiteLLM](https://docs.litellm.ai/docs/proxy/virtual_keys); [OmniRoute](https://github.com/diegosouzapw/OmniRoute); [9Router](https://github.com/decolua/9router)
- A defensible future acceptance plan must test streaming and non-stream responses; history/developer-role translation and unsupported parameters; simple and parallel tool cycles including Higgsfield discovery without paid generation; refresh/revocation; simultaneous users and noisy-neighbor limits; predictable 429 handling; disconnected/no-credit cases; logging redaction; and strict prohibition of unapproved paid fallbacks. These checks follow documented API restrictions, default exposure and routing behavior—not evidence that any candidate currently passes. [SIWC limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations); [OmniRoute subscription fail-closed mode](https://github.com/diegosouzapw/OmniRoute/blob/release/v3.8.53/docs/routing/SUBSCRIPTION_LADDER.md); [LiteLLM caveats](https://docs.litellm.ai/docs/providers/chatgpt)
- Keep a future gateway reachable only from the WebUI backend/private network; pin releases, require unique downstream credentials, rotate default/example secrets, protect management separately, disable unnecessary cloud/MCP/plugin/MITM features and minimize prompt retention. This is a recommended threat-model response to cited defaults, not an installation recipe. [CLIProxyAPI defaults](https://github.com/router-for-me/CLIProxyAPI/blob/v8.0.43/config.example.yaml); [9Router defaults](https://github.com/decolua/9router/blob/3a978a631ad65529c06e48ce495092d5bba29f46/.env.example); [OmniRoute defaults](https://github.com/diegosouzapw/OmniRoute/blob/412319f0bdda06a1c7db93dd62bdf8b6317edc1e/.env.example)

### Gaps

- No production suitability claim can be independently verified without a pinned candidate build, security review, realistic load and the live WebUI workflow. Release frequency and broad features establish maintenance/activity, not reliability. [Release evidence](https://github.com/router-for-me/CLIProxyAPI/releases); [OmniRoute releases](https://github.com/diegosouzapw/OmniRoute/releases); [LiteLLM releases](https://github.com/BerriAI/litellm/releases)
- No commitment to API billing, purchase, credential reuse, account authorization or shared subscription rollout is implied. Resolving the one-Pro-for-all requirement is a prerequisite, not a gateway setting that research can authorize. [OpenAI policy](https://help.openai.com/en/articles/10471989-openai-account-sharing-policy); [Anthropic policy](https://code.claude.com/docs/en/legal-and-compliance)

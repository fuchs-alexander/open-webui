# Konventionelle API-Gateways und Integrationsarchitektur für Posylka

Recherche: 26.10.2026. Ziel: Open WebUI v0.12.4, ChatGPT Pro (gewünscht: ein gemeinsam genutztes Konto), Claude-Abo oder API und OpenRouter. Ausschließlich öffentliche Dokumentation und Quellcode untersucht; keine Anmeldung, Zugangsdaten, Installation, Konfiguration oder Live-Tests. Aktuelle `main`-Quellen sind kein Nachweis, dass eine Funktion schon in einem bestimmten Release enthalten ist.

## 1. Welche Gateways unterstützen Abonnements tatsächlich und welche Grenzen gelten?

### Takeaway
LiteLLM besitzt inzwischen einen eigenen ChatGPT-Subscription-Provider mit Device-OAuth und Token-Refresh: Die pauschale Aussage „LiteLLM braucht dafür immer CLIProxyAPI“ ist falsch. Auch New API hat einen nativen Codex-Subscription-Kanal mit Credential-Import und Refresh; ein eigener interaktiver Erstanmeldungsflow wurde dort nicht nachgewiesen. Technische Funktionsfähigkeit ist keine Erlaubnis zur gemeinsamen Nutzung eines persönlichen Abos.

### Cited Findings
- **LiteLLM: ChatGPT Pro nativ, kein zusätzlicher Inferenz-Bridge nötig.** Der Provider `chatgpt/` verwendet den ChatGPT-Codex-Backend-Endpunkt, OAuth-Device-Flow, persistente Auth-Datei und Refresh. Er bietet `/responses` sowie für unterstützte Modelle `/chat/completions` durch Übersetzung. Das ist **nicht** der normale `openai/`-API-Key-Provider und **nicht** der neue SIWC-Registrierungsweg. — [Provider-Dokumentation](https://docs.litellm.ai/docs/providers/chatgpt)
- LiteLLM muss vor Proxy-Start interaktiv angemeldet werden; Worker/Async-Proxy können den erstmaligen Device-Flow nicht selbst bedienbar abschließen. Die Auth-Datei muss persistent und für Refresh beschreibbar sein. Die Dokumentation beschreibt Refresh-Races, getrennte Kopien und widerrufene Tokens ausdrücklich als Betriebsrisiken. — [Authentifizierung und Proxy-Betrieb](https://docs.litellm.ai/docs/providers/chatgpt#sign-in-before-starting-the-proxy)
- Ein LiteLLM-Prozess verwendet für `chatgpt/` genau einen Login; alle erlaubten virtuellen Schlüssel gehen über diesen Account. Clientseitig mitgesendete ChatGPT-Tokens werden ignoriert; mehrere ChatGPT-Konten erfordern laut Dokumentation getrennte Proxy-Deployments. Plan-/Workspace-Modellverfügbarkeit bleibt eingeschränkt, keine Freigabe aller OpenAI-API-Modelle. — [Credential Scope and Attribution](https://docs.litellm.ai/docs/providers/chatgpt#credential-scope-and-attribution)
- **LiteLLM: Claude-Abo-Weiterleitung vorhanden, aber kein WebUI-Abo-Login.** Seit v1.81.14 erkennt der Proxy vom Client übermittelte `sk-ant-oat...`-Tokens, setzt OAuth-Beta-Header und leitet sie an direkte `anthropic/`-Deployments weiter. Claude Code übernimmt Anmeldung, Speicherung und Refresh; LiteLLM speichert oder erneuert den Claude-Login nicht. Dokumentiert für Claude Code mit eigenem Abo pro Nutzer, nicht als gemeinsam genutztes Claude-Abo für WebUI. — [Claude-Subscription-Tutorial](https://docs.litellm.ai/docs/tutorials/claude_code_max_subscription)
- **Anthropic untersagt die relevante Umwidmung ausdrücklich:** Entwickler sollen API-Schlüssel/unterstützte Cloud-Provider nutzen; Drittanbieter dürfen keinen Claude.ai-Login für eigene Anwendungen anbieten und keine Free-/Pro-/Max-Credentials im Auftrag ihrer Nutzer routen. Native OAuth-Nutzung ist für Claude Code und andere native Anthropic-Anwendungen bestimmt. Die Möglichkeit, unverändertes Claude Code mit eigenem Endnutzer-Login zu hosten, ist kein allgemeiner WebUI-Bridge-Freibrief. — [Anthropic Legal and compliance, Authentication and credential use](https://code.claude.com/docs/en/legal-and-compliance)
- **New API: nativer ChatGPT-Subscription-Kanal existiert.** `ChannelTypeCodex = 57`, Name `ChatGPT Subscription (Codex)`, Standardbasis `https://chatgpt.com`. `OpenRouter = 20`, `Anthropic = 14`, `Sub2API = 59` sind getrennte Kanaltypen. `Sub2API` im Dropdown ist nicht gleichbedeutend mit einem eingebauten Claude-Abo-OAuth-Client. — [Kanaldefinitionen](https://github.com/QuantumNous/new-api/blob/main/constant/channel.go)
- New APIs Codex-Adapter akzeptiert JSON mit `access_token` und `account_id`, optional `refresh_token`; setzt Bearer- und `chatgpt-account-id`-Header und ruft `/backend-api/codex/responses` auf. Direkte Chat-Completions-/Messages-Aufrufe werden im Adapter abgewiesen. Ob eine vorgelagerte interne Konversionsroute den konkreten Kanal dennoch nutzbar macht, muss separat geprüft werden. — [Adapter](https://github.com/QuantumNous/new-api/blob/main/relay/channel/codex/adaptor.go), [OAuth-Key-Schema](https://github.com/QuantumNous/new-api/blob/main/relay/channel/codex/oauth_key.go)
- New API kann importierte Codex-Refresh-Tokens mit festem Codex-OAuth-Client erneuern und aktualisierte Credentials in der Kanal-Datenbank speichern; ein Master-Node-Task erneuert geeignete Einzel-Key-Kanäle automatisch. Das belegt **native Backend-Integration und Refresh**, nicht native SIWC-Registrierung oder einen Browser-Login zur initialen Token-Ausstellung. — [Refresh](https://github.com/QuantumNous/new-api/blob/main/service/codex_credential_refresh.go), [OAuth-Service](https://github.com/QuantumNous/new-api/blob/main/service/codex_oauth.go), [Refresh-Task](https://github.com/QuantumNous/new-api/blob/main/service/codex_credential_refresh_task.go)
- **Portkey OSS:** Das dokumentierte Gateway nimmt Provider-API-Schlüssel entgegen; weder ein ChatGPT-/Codex- noch Claude-Subscription-OAuth-Provider wurde in den untersuchten Provider-/OAuth-Pfaden nachgewiesen. Für Abo-Zugang daher nicht als eigenständige Lösung einplanen; ein externer kompatibler Bridge-Endpunkt wäre eine zusätzliche Komponente. — [OSS-README und Providerliste](https://github.com/Portkey-AI/gateway), [Provider-Quellbaum](https://github.com/Portkey-AI/gateway/tree/main/src/providers)
- **Open WebUI nativ:** Mehrere URL-/Key-Verbindungen sind vorhanden; die offizielle OpenAI-Anleitung beschreibt separat ausgestellte API-Schlüssel, nicht ChatGPT-Pro-Anmeldung. Ein Frontend-/IdP-OAuth-Login oder OAuth-Weiterleitung zu einem Gateway ist nicht automatisch Provider-Abozugang. — [OpenAI-Verbindungen](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-openai), [LiteLLM-WebUI-OIDC-Architektur](https://docs.litellm.ai/docs/tutorials/openwebui_org_rollout)
- **Offizieller OpenAI-Gegenentwurf:** Sign in with ChatGPT erlaubt mittlerweile geeignete Responses-Anfragen aus Open-Source-/lokal gehosteten Apps auf dem Plan des autorisierenden Nutzers, mit eigener dynamischer OAuth-Clientregistrierung und stabilem Host-Identifier. Für bezahlte/remote gehostete Apps verweist OpenAI auf ein Interessenformular. Der registrierte Client ist an Nutzer und Workspace gebunden. Das ist keine generelle Genehmigung, ein Pro-Konto als Team-Backend zu verwenden. — [SIWC ChatGPT plan usage](https://developers.openai.com/siwc/token-sharing-open-source)

### Inferences
- Für **ChatGPT-Abo + Claude API + OpenRouter** ist LiteLLM technisch der stärkste Ein-Gateway-Kandidat dieser Auswahl. Ein CLIProxyAPI davor ist für LiteLLMs dokumentierten ChatGPT-Weg redundant; verbindliche Freigabe des Kontomodells bleibt Voraussetzung.
- Für **gemeinsames ChatGPT-Pro-Konto + gemeinsames Claude-Abo** erfüllt keines dieser Produkte nachgewiesen sowohl technische als auch vertragliche Anforderungen. Claude API oder Claude via OpenRouter ist der belastbarere Mehrbenutzerweg; API-Kosten sind zusätzlich zum Claude-Abo.
- Native Codex-Unterstützung in New API nicht übersehen, aber Credential-Import nicht als gleichwertig zu einem eigenen, vom Nutzer autorisierten SIWC-Onboarding verkaufen. Keine vorhandenen Codex-/OpenCode-Anmeldedaten dafür kopieren.

### Gaps
- Keine gemeinsame Pro-Kontonutzung durch mehrere natürliche Personen als erlaubt verifiziert. Die separate OpenAI-Account-Sharing-Hilfeseite ließ sich beim Abruf nicht öffnen (403); daraus folgt keine Erlaubnis. SIWC-Dokumentation ist nutzer-/workspacebezogen, keine Freigabe des gewünschten Sharing-Modells.
- Nicht bestimmt: erstes stabiles LiteLLM-/New-API-Release mit allen beschriebenen Funktionen; aktuelle Dokumentation und `main` müssen vor einer Entscheidung auf einen gepinnten Release abgebildet werden.
- New API: kein initialer Codex-Login-/Device-Code-Flow in untersuchten Codex-Dateien gefunden; eventuell zusätzliche UI-/Release-Funktionen bleiben unbestätigt. Kein nativer Claude-Abo-Login samt Refresh nachgewiesen.
- Kein Nachweis, dass LiteLLM oder New API den neuen offiziellen SIWC-Dynamic-Client-/Host-ID-Weg implementieren. Ihre nachgewiesenen Codex-Backend-Wege sind davon zu unterscheiden.

## 2. Authentifizierung, Kostenkontrolle, OpenRouter und Protokollkompatibilität

### Takeaway
Gateways bringen Schlüssel-, Quoten- und Routingkontrolle, aber nicht automatisch die Identität der einzelnen WebUI-Nutzer. Eine gemeinsam gespeicherte Gateway-Verbindung mit einem einzigen Schlüssel liefert zunächst eine gemeinsame Kostenstelle; persönliche Zurechnung muss bewusst durchgängig gebaut und getestet werden.

### Cited Findings
- **LiteLLM Governance:** Virtuelle Schlüssel mit Modell-Allowlist, Nutzer-/Team-Zuordnung, Budgets, RPM-/TPM-Limits und Spend-Auswertung sind dokumentiert. Die persistente Schlüsselverwaltung benötigt PostgreSQL und einen Master-Key. Ein vom Admin erstellter Key benötigt explizite `user_id`, um einem Nutzer zu gehören. — [Virtual Keys](https://docs.litellm.ai/docs/proxy/virtual_keys)
- **Subscription-Kosten sind nicht normale API-Kosten:** Für LiteLLMs `chatgpt/` stehen im Preisverzeichnis keine Preise, deshalb ist dokumentierter Spend $0; `max_budget` greift dann nicht. RPM-/TPM-Limits sind hier die empfohlenen Nutzungsgrenzen. Bei weitergereichten Claude-Abo-Tokens berechnet LiteLLM dagegen API-Listenpreis-Äquivalente: Diese taugen als künstliche Usage-Kappen, nicht als tatsächliche Abo-Rechnung. — [ChatGPT Attribution](https://docs.litellm.ai/docs/providers/chatgpt#credential-scope-and-attribution), [Claude Attribution and cost](https://docs.litellm.ai/docs/tutorials/claude_code_max_subscription#attribution-and-cost)
- **Echte WebUI-Nutzeridentität via OIDC:** LiteLLM dokumentiert Open WebUI v0.12.0 mit `auth_type: system_oauth`, Weiterleitung des Nutzer-IdP-Tokens und JWT-Prüfung im Gateway. JWT-Auth benötigt LiteLLM Enterprise. WebUI-API-Key-Anfragen haben dabei keine OAuth-Sitzung und funktionieren nicht einfach identisch. — [Open WebUI for Organizations](https://docs.litellm.ai/docs/tutorials/openwebui_org_rollout)
- **OpenRouter in LiteLLM ist ein dedizierter Provider**, nicht nur ein generischer OpenAI-Endpunkt: `openrouter/<provider>/<model>`, `OPENROUTER_API_KEY`, eigene Site-/App-Header und Durchreichen von OpenRouter-Parametern; Text/Chat/Vision/Embeddings dokumentiert. — [OpenRouter-Provider](https://docs.litellm.ai/docs/providers/openrouter)
- **OpenRouter in Portkey ist ebenfalls nativ:** eigener Provider setzt Bearer-API-Key, `HTTP-Referer`, `X-Title` und `/v1/chat/completions`. Der untersuchte Provider-Endpunktmapper implementiert explizit Chat Completions, keine allgemeine Zusage für alle OpenRouter-Responses-Funktionen. — [OpenRouter-Adapter](https://github.com/Portkey-AI/gateway/blob/main/src/providers/openrouter/api.ts)
- **New API Governance:** Webkonsole mit Nutzern/Gruppen/Rechten, API-Key-Einschränkungen, Quoten, Usage-Logs, Preisformeln, Prioritäten/Gewichten, Retry, Affinity und mehreren Upstream-Keys. OAuth/OIDC, Passkeys und 2FA im README beziehen sich auf Gateway-Zugang und sind kein Beleg für Modellanbieter-Abos. OpenRouter hat Kanaltyp und Standard-URL. — [README](https://github.com/QuantumNous/new-api#capabilities), [OpenRouter-Kanal](https://github.com/QuantumNous/new-api/blob/main/constant/channel.go)
- **SSE/Tools/Responses in New API:** Chat Completions, Responses, Anthropic Messages und Gemini einschließlich Streaming und Tool-/Reasoning-Konversion werden unterstützt; das Projekt warnt ausdrücklich vor unvollständiger Feld-/Tool-Abbildung je Konversionspfad. Die Codex-Route setzt `store=false`, entfernt `max_output_tokens`, Temperatur und Penalties. — [Protokolle und Einschränkungen](https://github.com/QuantumNous/new-api#capabilities), [Codex-Adapter](https://github.com/QuantumNous/new-api/blob/main/relay/channel/codex/adaptor.go)
- **LiteLLM Responses:** `/responses` ist ein eigener unterstützter API-Endpunkt; `chatgpt/` ist Responses-nativ, kann Chat-Completions übersetzen und SSE bzw. aggregierte Nichtstream-Antworten liefern. Der Provider entfernt nicht unterstützte Token-Limit-Felder und `metadata`; nicht alle Requests sind ohne Anpassung identisch zur OpenAI Platform API. — [Responses API](https://docs.litellm.ai/docs/response_api), [ChatGPT-Provider](https://docs.litellm.ai/docs/providers/chatgpt)
- **Portkey:** OSS-README dokumentiert Streaming bei OpenAI/Anthropic und Routing/Fallbacks. Im Quellcode ist zusätzlich ein Responses-Handler vorhanden. Daraus folgt kein universeller Feature-Paritätsnachweis für jede Provider-/Tool-Kombination. — [Provider- und Featureliste](https://github.com/Portkey-AI/gateway), [Responses-Handler](https://github.com/Portkey-AI/gateway/blob/main/src/handlers/modelResponsesHandler.ts)
- **Open WebUI v0.12.4 Baseline ist bereits Responses-fähig:** Der getaggte Router enthält Konversion von Messages, Funktionsdefinitionen, `tool_choice`, Tool-Outputs sowie `/responses`-Weiterleitung, aktiviert über `api_type == 'responses'`. Damit ist ein Gateway allein wegen „WebUI kann nur Chat Completions“ nicht erforderlich. — [v0.12.4 Router, insbesondere convert_to_responses_payload und generate_chat_completion](https://github.com/open-webui/open-webui/blob/v0.12.4/backend/open_webui/routers/openai.py)
- Open-WebUI-Dokumentation nennt Responses experimentell und unterstützt Tool-Reinvocations/Streaming; Standard ist stateless. Stateful-Modus soll nur mit nachweislich geeignetem Upstream verwendet werden. — [Open Responses](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-open-responses)
- **Claude API direkt als Baseline:** WebUI dokumentiert direkten Anthropic-Zugang über dessen OpenAI-kompatiblen Chat-Endpunkt, mit Streaming und Tools; zugleich weist die Dokumentation auf Anthropic-Einstufung „Evaluation/Testing“ und fehlende vollständige native Features hin. Für native Messages-Funktionen werden Pipe oder LiteLLM genannt. Diese Website ist eine aktuelle Dokumentation, kein eigenständiger v0.12.4-Abnahmetest. — [Anthropic-Anleitung](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-anthropic)

### Inferences
- Für per-person harte Quoten **nicht** nur einen systemweiten Gateway-Key hinterlegen und annehmen, WebUI-Logins würden automatisch zu Gateway-Nutzern. Optionen: individuelle Gateway-Keys/verifizierte nutzerspezifische Übergabe oder IdP-JWT-Integration; Identität und Rechte in beiden Schichten abstimmen.
- Nutzer-ID-/Info-Header sind Metadaten, solange der Gateway sie nicht aus einer ausschließlich vertrauenswürdigen, authentifizierten WebUI-Verbindung prüft. Clientkontrollierte `user`-Felder sind keine verlässliche Autorisierung.
- Tool-Calling-Fähigkeit des Gateways ersetzt keine End-to-End-Abnahme: WebUI → Gateway → konkreter Provider → Tool-Result → zweiter Modellturn. Providerseitige Websuche, externe MCP-Tools und klassische JSON-Funktionen getrennt testen.
- In New API kann internes Quoten-/Preis-Rechnen Abo-Nutzung künstlich verteilen, aber daraus weder tatsächliche Pro-Dollar-Kosten noch eine exakte verbleibende Anbieter-Planquote ableiten.

### Gaps
- Keine im Rechercheumfang verifizierte, kostenlose Standardkonfiguration, die individuelle WebUI-Identitäten ohne Zusatzarbeit sicher auf LiteLLM-/New-API-/Portkey-Keys abbildet.
- Portkeys genaue Self-hosted-Governance-Grenzen ändern sich durch 2.0 (siehe nächste Frage); OSS-README-Marketing nicht als Zusage für kostenlose harte Budgets/RBAC missverstehen.
- End-to-End-SSE-Abbruch, parallele Tool-Calls, Bildinputs, Reasoning, lange Laufzeiten, Titel-/Tag-Hintergrundanfragen und Responses-Tool-Mehrturns wurden nicht live geprüft.

## 3. Lizenz, Betriebsaufwand und Mehrwert einer zusätzlichen Gateway-Schicht

### Takeaway
Für eine kleine einzelne WebUI-Instanz sind mehrere native Verbindungen die wirtschaftliche Baseline. Wenn ein zentrales Gateway gebraucht wird, ist LiteLLM derzeit am stärksten belegt; ein zusätzlicher Abo-Bridge-Hop lohnt sich erst bei einer konkret nachgewiesenen Lücke und löst keine Nutzungsrechtsfrage.

### Cited Findings
- **LiteLLM-Lizenz:** MIT außerhalb `enterprise/`, dort kommerzielle Lizenz. Basis-Virtual-Keys/Spend-Verwaltung sind öffentlich dokumentiert; JWT-Auth und Key-Regeneration/Rotation sind ausdrücklich Enterprise-Funktionen. Nicht pauschal alle Governance-Funktionen als kostenlos oder alle als kostenpflichtig darstellen. — [LICENSE](https://github.com/BerriAI/litellm/blob/main/LICENSE), [Virtual Keys und Rotation](https://docs.litellm.ai/docs/proxy/virtual_keys), [WebUI JWT-Lizenzanforderung](https://docs.litellm.ai/docs/tutorials/openwebui_org_rollout)
- **LiteLLM-Betrieb:** einfacher Proxy-Prozess möglich; persistente Keys/Dashboard/Spend benötigen PostgreSQL. ChatGPT erfordert zusätzliche persistent beschreibbare Tokenablage, bewusstes Initial-Onboarding und Wiederanmeldung bei Widerruf. — [Virtual-Key-Voraussetzungen](https://docs.litellm.ai/docs/proxy/virtual_keys), [ChatGPT-Proxy-Betrieb](https://docs.litellm.ai/docs/providers/chatgpt)
- **Portkey:** öffentlicher Gateway-Kern MIT, Node/npm- oder Docker-Betrieb mit lokaler Konsole. Das README trennt Enterprise-/Hosted-Funktionen wie Organisationsmanagement, fortgeschrittene Governance/Observability und Promptverwaltung vom Kern. Zugleich kündigt es **Gateway 2.0 als Pre-Release** an, das Enterprise-Core-Funktionen in Open Source überführt. Daher weder alte Feature-Grenzen dauerhaft festschreiben noch Pre-Release-Ankündigungen als produktiv frei verfügbare Komplettplattform behandeln. — [README einschließlich 2.0-Hinweis, Enterprise und Feature-Fußnoten](https://github.com/Portkey-AI/gateway)
- **New API:** AGPLv3 mit zusätzlichen §7-Attributionsbedingungen: Autorenhinweis und sichtbarer Originalprojekt-Link in modifizierten UIs erhalten. Kommerzielle Lizenzanfrage möglich, falls AGPL-Pflichten nicht akzeptabel sind; keine belegte Pflicht, für den privaten Standardbetrieb einen Cloudplan zu kaufen. — [Lizenzabschnitt](https://github.com/QuantumNous/new-api#license), [LICENSE](https://github.com/QuantumNous/new-api/blob/main/LICENSE), [NOTICE](https://github.com/QuantumNous/new-api/blob/main/NOTICE)
- New API kann als einzelner Container mit SQLite starten. Repository-Compose verwendet New API + PostgreSQL + Redis; Shared-Redis ist für gemeinsame Mehrknoten-Rate-Limits wichtig. Backups umfassen Hauptdatenbank und Datenverzeichnis, Konsole braucht HTTPS/geeignete Proxy-Settings. — [Quickstart/Deployment](https://github.com/QuantumNous/new-api#quick-start)
- **WebUI-Baseline:** mehrere Providerverbindungen mit Prefix und Modell-Allowlist werden bereits unterstützt; `v0.12.4` lizenziert Nutzung/Änderung unter eigener Open-WebUI-Lizenz mit Branding-Regeln und Ausnahmen, nicht pauschal MIT. Projektvorgabe, Branding zu respektieren, bleibt maßgeblich. — [Verbindungsverwaltung](https://docs.openwebui.com/getting-started/quick-start/connect-a-provider/starting-with-openai), [v0.12.4 LICENSE](https://github.com/open-webui/open-webui/blob/v0.12.4/LICENSE)

### Inferences
- **Minimalarchitektur:** WebUI → OpenRouter für bezahlt abgerechnete Mehranbieter-API; optional eigener direkter Anthropic-API-Endpunkt. ChatGPT Pro separat nur über freigegebenen, korrekt onboardeten Weg. Kein Gateway bloß zur optischen Vereinheitlichung erforderlich.
- **Ein-Gateway-Architektur:** WebUI → LiteLLM → ChatGPT-Subscription-Provider / Anthropic API / OpenRouter. Vorteil: zentraler Modellkatalog, Aliase, globale Limits, einheitliches Logging und Schlüsselwechsel. Kosten: Dienst + bei Governance PostgreSQL + Token-Refresh-Betrieb; Shared-Pro-Freigabe bleibt ungeklärt.
- **Alternative:** WebUI → New API → nativer Codex-Kanal / Anthropic API / OpenRouter. Gut für Webkonsole, lokale Quoten und Kanalverwaltung, aber mehr UI-/Preis-/Kontenverwaltung und AGPL-Pflichten. Initialer Codex-Credential-Import ist hier die entscheidende noch unaufgelöste Integrationsstelle.
- **Zwei-Hop-Schema:** WebUI → Governance-Gateway → CLIProxyAPI/anderer Subscription-Bridge → Anbieter. Nur sinnvoll, wenn der Bridge eine benötigte, erlaubte Auth-/Protokollfunktion exklusiv bereitstellt und zentrale Governance wirklich benötigt wird. Nachteile: zusätzliche Ausfallstelle, Timeout-/SSE- und Tool-Konversion, doppelte Modellmappings, getrennte Logs und Refresh-Zustände. Der Gateway macht eine unzulässige Abo-Weitergabe nicht zulässig.
- **Für Posylka priorisieren:** (1) Kontonutzung/Sharing und Anbieterfreigabe klären; (2) offizielle SIWC-Eignung für diesen gehosteten Betrieb prüfen; (3) getrennte API-Kosten für Claude/OpenRouter akzeptieren oder ablehnen; (4) native Verbindungen als Vergleichsbasis; (5) LiteLLM nur bei konkretem Governance- oder Bridge-Mehrwert; (6) erst danach ggf. zweite Proxy-Schicht. Keine stille kostenpflichtige API-Ausweichroute bei Abo-Erschöpfung.

### Gaps
- Keine belastbaren eigenen RAM-/CPU-/Latenzmessungen; „leichtgewichtig“ und Submillisekundenangaben der Anbieter sind keine Kapazitätsplanung für diesen Server.
- Portkey 2.0: genaue stabile Version, Lizenz-/Featurematrix und Self-hosted-Control-Plane-Abhängigkeiten vor Beschaffung neu prüfen.
- Für Produktionsfreigabe fehlen gepinnte Versionen und Tests für frischen Login, Refresh nach Neustart, Widerruf, harte Limits bei Parallelität, Nutzerattribution, Background-Task-Kosten, Streaming-Abbruch und Mehrturn-Tools.
